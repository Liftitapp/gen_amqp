## (B) Agent-to-agent communication primitives

**Finding: built-in agent-to-agent is first class via 4 tools + A2A protocol + Workflow Engine. No new `delegate()` needed.**

### Three coexisting mechanisms

1. **Direct in-process call via builtin tools** — `crates/openfang-runtime/src/tool_runner.rs` (≈line 280):
   ```rust
   "agent_send"  =&gt; tool_agent_send(input, kernel).await,
   "agent_spawn" =&gt; tool_agent_spawn(input, kernel, caller_agent_id).await,
   "agent_list"  =&gt; tool_agent_list(kernel),
   "agent_kill"  =&gt; tool_agent_kill(input, kernel),
   ```
   `tool_agent_send` (≈1040–1068) delegates to `kernel_handle.send_to_agent(agent_id, message)`. **Critical semantics**: callee sees ONLY the passed message string — *not* the caller's session history. The callee runs in its own session. Caller context is NOT automatically forwarded. You must manually stuff context into the message.

   Recursion bounded by `MAX_AGENT_CALL_DEPTH = 5` via the `AGENT_CALL_DEPTH` task-local cell. Deeper chains are rejected with: *"Inter-agent call depth exceeded (max 5). A-&gt;B-&gt;C chain is too deep. Use the task queue instead."*

2. **A2A (Agent-to-Agent) protocol** — `crates/openfang-runtime/src/a2a.rs`. JSON-RPC 2.0 over HTTP, compatible with Google's A2A / agent-card standard. OpenFang is both server (publishes Agent Cards at `/.well-known/agent.json`, accepts `POST /a2a/tasks/send`) and client (`A2aClient`). Task lifecycle: `Submitted → Working → InputRequired|Completed|Failed|Cancelled`, tracked in `A2aTaskStore` (1000-slot bounded). Used for cross-*framework* / cross-process agent interop — overkill for same-daemon use.

3. **Workflow Engine** — `docs/workflows.md` + `crates/openfang-kernel/src/workflow.rs`. Declarative pipelines register via `POST /api/workflows`. Modes: `sequential`, `fan_out`, `collect`, `conditional`, `loop`. Output passes via `{{input}}` and named `output_var`. Error modes: `fail` / `skip` / `retry` (with `max_retries`).

### Supervisor / orchestrator support

- There IS a `Supervisor` subsystem in the kernel (boot step 7), primarily for lifecycle / restart supervision of background agents.
- The `orchestrator` agent ships as the canonical delegation agent — it is *a prompt pattern*, not a framework primitive. `agents/orchestrator/agent.toml` prompts it to do `agent_list → agent_send → synthesize`. Capabilities: `tools = ["agent_send", "agent_spawn", "agent_list", "agent_kill", "memory_store", "memory_recall", "file_read", "file_write"]`, `agent_spawn = true`, `agent_message = ["*"]`.
- No hierarchical tree like CrewAI/AutoGen — it's flat registry + per-call depth counter.

### Context passing: B does NOT see A's session. You have three options:
- Put the context in the `agent_send` message body (what orchestrator does).
- Use the **shared memory namespace** — fixed agent ID `00000000-...01` — and have both ends read/write (`memory_read = ["*"]`).
- Use **`CanonicalSession` (schema v5)**: same user across channels gets compacted summary injected into system prompt of whichever agent replies.

## (C) Channels and routing (Slack specifically)

**Finding: OpenFang has a real `AgentRouter` with a 4-tier priority that DOES support multi-agent routing — but NOT on per-Slack-app-ID (one bot token is bound to one adapter instance globally).**

### Router priority (confirmed from `crates/openfang-channels/src/router.rs`)
1. **Bindings** (most specific → least specific)
2. **Direct routes** (channel + user ID)
3. **User defaults**
4. **System / channel default**

### `AgentBinding.match_rule` fields
```
channel:     Option&lt;String&gt;   // channel-type: "slack" | "telegram" | ...
account_id:  Option&lt;String&gt;   // bot/account ID within that channel
peer_id:     Option&lt;String&gt;   // user ID / DM target
guild_id:    Option&lt;String&gt;   // workspace/server/guild
roles:       Vec&lt;String&gt;      // user role match
```
`binding_matches()`: all specified fields must match; for `roles`, any-of.

### Slack adapter specifics (`crates/openfang-channels/src/slack.rs` + `docs/channel-adapters.md`)
Config schema:
```toml
[channels.slack]
bot_token_env   = "SLACK_BOT_TOKEN"
app_token_env   = "SLACK_APP_TOKEN"
allowed_channels = []
default_agent   = "ops"

[channels.slack.overrides]
model              = "..."              # per-channel model override
system_prompt      = "..."
dm_policy          = "respond"          # respond | allowed_only | ignore
group_policy       = "mention_only"     # all | mention_only | commands_only | ignore
rate_limit_per_user= 10
threading          = true
output_format      = "slack_mrkdwn"
```

### Key capability gaps for your use case
1. **One Slack adapter instance = one bot token = one `default_agent`.** The adapter struct holds a *single* `app_token`/`bot_token` pair. Multiple Slack App IDs → different agents is **NOT supported by a single adapter instance**. Workaround: run two Slack bridges (two App IDs) each configured with its own `default_agent`; or use router bindings below.
2. **Router bindings CAN override default_agent per Slack channel / user / role.** Since `match_rule` supports `channel="slack"`, `account_id=&lt;bot&gt;`, `guild_id=&lt;workspace&gt;`, you can map:
   - Slack workspace X (guild_id) → agent A
   - Slack user Y (peer_id) → agent B
   - Specific role Z → agent C
3. **`group_policy = "mention_only"`** is a **per-channel filter** applied in the adapter *before* any agent runs — zero LLM cost for ignored messages. It does NOT filter across agents (there's no "multiple agents race for first responder" behavior).
4. **No first-responder / election mechanism.** Router resolves deterministically to *exactly one* agent per incoming message. `resolve_broadcast()` exists and returns a `Vec&lt;(String, Option&lt;AgentId&gt;)&gt;` but is opt-in and only for broadcast peers configured in `BroadcastConfig`.
5. **Mention-pattern routing**: the Slack adapter flags `was_mentioned` in metadata, but the router doesn't match on mention text. You would have to customize router bindings or have the receiving agent self-route via `agent_send`.

### Per-user cross-channel identity
```toml
[[users]]
name = "Alice"
role = "owner"

[users.channel_bindings]
telegram = "123456"
slack    = "U0ABCDEFG"
```
This plus `CanonicalSession` gives Alice a unified conversation state across channels.

## (F) Conversation / session state

From architecture doc + `openfang-memory` crate:

- **Per-agent session**: "Each agent has a session containing its message history (user/assistant/tool use/tool result/image). Sessions track context-window token counts. Persisted to SQLite, restored on reboot." One SQLite DB, multiple session rows, keyed by agent.
- **Per-agent KV memory**: `memory_store` / `memory_recall` — scoped to the agent, `memory_write = ["self.*"]` by default.
- **Shared memory namespace** (agent_id `00000000-...01`): cross-agent data sharing. Your router → specialist design can push the user's original message there; specialist reads it with `memory_recall`.
- **CanonicalSession (schema v5)**: per-user cross-channel context, compacted summary injected into system prompt at the next turn.
- **`usage_events` table** (per agent + per model): token counts, cost, metering. Good for debugging token blowouts post-migration.
- **Knowledge graph** (optional): entities + typed relations per agent.

**For router+specialist design:**
- Option 1 (simplest): router stuffs the user's original message verbatim into `agent_send` body. No shared state needed.
- Option 2: router writes original message + metadata to shared memory under a request-id key, calls `agent_send` with just the key; specialist does `memory_recall`.
- Option 3: use `CanonicalSession` so that specialist agent already has the user's prior turns without explicit transfer — but only works if both agents reply to the *same user*, which they do in your Slack use case.

## (H) Token optimization mechanisms

Confirmed present:

1. **Per-agent `capabilities.tools` allowlist** — THE primary token lever. Lists of MCP tools included vs excluded directly shrink the schema payload per request. See §D.
2. **Fallback models** (`[[fallback_models]]`) — when primary rate-limits, auto-reroute. Good for your 200K TPM Vertex hit: set Groq/Gemini Flash as fallback.
3. **Quota enforcement** (`max_llm_tokens_per_hour`) — per agent. Can pre-empt hitting Vertex TPM.
4. **Channel overrides for `model` and `system_prompt`** — you can point Slack DM traffic at a cheaper model than Slack mentions, etc.
5. **Auto-compaction**: sessions compact on demand; `CanonicalSession` compaction injects summaries.
6. **Context budget** (`crates/openfang-runtime/src/context_budget.rs`): budgets session tokens before the LLM call.
7. **Sub-agent depth tool stripping** (`SUBAGENT_DENY_ALWAYS`, `SUBAGENT_DENY_LEAF`): at depth &gt; 0 sub-agents automatically lose cron/schedule/hand/process tools; at leaf depth they also lose `agent_spawn` / `agent_kill`. Safety, not token-savings, but does shrink the tool-schema payload for callees.
8. **Per-channel rate limit** (`rate_limit_per_user`) — throttles before hitting the LLM.
9. **Hand policies / `group_policy = "mention_only"`** — filters before LLM. Zero tokens for ignored messages.
10. **`[resources] max_concurrent_tools`** — caps parallel tool execution; indirectly reduces retried/duplicated calls.

Confirmed ABSENT:

- **Dynamic / lazy MCP tool loading**: no "only attach Postgres tools if user mentions database" — the tool list is assembled once per request based on static manifest, not query-aware.
- **Automatic schema compression / summarization of tool descriptions**: not present. Each tool's full `description` + JSON Schema goes in the request every turn.
- **Per-agent MCP server selection**: not present. Only per-agent *tool-name* selection via `capabilities.tools`.

### Bullets

- **If YES — how to specify on agent.toml**: Use `capabilities.tools = ["..."]` with **exact full names only**. No wildcards or prefixes (`"mcp_github_*"` will NOT match — the predicate is `d == &amp;t.name`, strict equality). The only recognized wildcard is the literal single-element `"*"` which means "all tools". MCP names must be the namespaced form `mcp_{server}_{tool}` lowercased/normalized (see `crates/openfang-runtime/src/mcp.rs` lines 338-395 — dashes/dots/spaces become `_`). Empty or missing `capabilities.tools` → unrestricted (all tools). There are two additional orthogonal filters applied AFTER: `tool_allowlist` / `tool_blocklist` (case-insensitive exact match, lines 5640-5665). `mcp_servers` still applies as a coarser server-level gate: if set, only tools whose server matches survive into the declared-tools filter.

- **Version difference (v0.2.3 vs main)**: **Different behavior — CRITICAL for you.** v0.2.3 `available_tools` (single function, line 3900) does NOT read `manifest.capabilities.tools` at all. Filtering is driven by `ToolProfile` (builtin tiers) plus `Capability::ToolInvoke(name)` / `Capability::ToolAll` from the runtime capability system (lines 3979-3995). MCP tools are added via `mcp_servers` allowlist only (lines 3957-3977) — there is no per-tool-name filter on MCP. So in your prod version, declaring `capabilities.tools = ["mcp_github_list_commits"]` has NO EFFECT on MCP payload; the agent still receives every tool from every allowlisted MCP server. To get the per-name MCP filter you must upgrade past v0.2.3 (feature landed in the rewrite that introduced `available_tools_with_registry`). Until then, the lever is `mcp_servers` (coarse, server-level) plus `ToolInvoke` capability grants at runtime.
