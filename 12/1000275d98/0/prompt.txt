# /sc:analyze - Code Analysis and Quality Assessment

## Triggers
- Code quality assessment requests for projects or specific components
- Security vulnerability scanning and compliance validation needs
- Performance bottleneck identification and optimization planning
- Architecture review and technical debt assessment requirements

## Usage
```
/sc:analyze [target] [--focus quality|security|performance|architecture] [--depth quick|deep] [--format text|json|report]
```

## Behavioral Flow
1. **Discover**: Categorize source files using language detection and project analysis
2. **Scan**: Apply domain-specific analysis techniques and pattern matching
3. **Evaluate**: Generate prioritized findings with severity ratings and impact assessment
4. **Recommend**: Create actionable recommendations with implementation guidance
5. **Report**: Present comprehensive analysis with metrics and improvement roadmap

Key behaviors:
- Multi-domain analysis combining static analysis and heuristic evaluation
- Intelligent file discovery and language-specific pattern recognition
- Severity-based prioritization of findings and recommendations
- Comprehensive reporting with metrics, trends, and actionable insights

## Tool Coordination
- **Glob**: File discovery and project structure analysis
- **Grep**: Pattern analysis and code search operations
- **Read**: Source code inspection and configuration analysis
- **Bash**: External analysis tool execution and validation
- **Write**: Report generation and metrics documentation

## Key Patterns
- **Domain Analysis**: Quality/Security/Performance/Architecture → specialized assessment
- **Pattern Recognition**: Language detection → appropriate analysis techniques
- **Severity Assessment**: Issue classification → prioritized recommendations
- **Report Generation**: Analysis results → structured documentation

## Examples

### Comprehensive Project Analysis
```
/sc:analyze
# Multi-domain analysis of entire project
# Generates comprehensive report with key findings and roadmap
```

### Focused Security Assessment

## 4. Best Practices for Terraform Provider Version Management

### Where to Pin Versions

**Recommended approach: Pin in root modules, use flexible constraints in shared/child modules.**

Your current setup already follows a pattern where each root module (e.g., `networking/dns/`, `apps/gke/`, etc.) has its own `versions.tf`. This is actually a good foundation, but there are improvements to consider:

#### Current Pattern in Your Repo (Repeated per Root Module)
```hcl
terraform {
  required_version = "~> 1.11"
  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~>6.26"
    }
    cloudflare = {
      source  = "cloudflare/cloudflare"
      version = "~> 4.0"
    }
  }
}
```

#### Best Practices

1. **Root modules should use tight constraints**: Use the pessimistic constraint operator (`~>`) with specific patch versions for production stability:
   ```hcl
   # In root modules
   google = {
     source  = "hashicorp/google"
     version = "~> 6.27.0"  # Allows 6.27.x but not 6.28.0
   }
   ```

2. **Child/shared modules should use wide constraints**: Reusable modules should specify the minimum version they require but not be overly restrictive:
   ```hcl
   # In reusable modules
   google = {
     source  = "hashicorp/google"
     version = ">= 6.0"
   }
   ```

3. **Always commit `.terraform.lock.hcl`**: You are already doing this. The lockfile provides reproducible builds regardless of the constraint syntax.

4. **Use `required_version` consistently**: Your `~> 1.11` constraint is appropriate -- it allows 1.11.x but not 1.12+. When upgrading, update this across all modules.

5. **Centralized version management options**:
   - **Option A (your current approach)**: Each root module manages its own versions. Simple but leads to version drift between modules.
   - **Option B**: Use a shared `.tf` file via symlinks or a code generation tool to maintain versions in one place.
   - **Option C**: Use Terragrunt with a centralized `generate` block to inject provider versions into all modules.
   - **Option D**: Use a CI/CD pipeline that validates all modules use the same provider versions.

6. **For your specific repo**: Since you have 33+ root modules all with nearly identical `versions.tf` files, consider a script or CI check that ensures all modules specify the same provider versions.

## 5. Terraform Upgrade Path from 1.11.2 to 1.14.5

### General Terraform Upgrade Rules

HashiCorp's official guidance:

1. **You can skip minor versions**: Terraform guarantees state file forward compatibility. You can upgrade from 1.11 directly to 1.14 without stopping at 1.12 and 1.13.

2. **However, incremental upgrades are RECOMMENDED** because:
   - Each minor version may introduce deprecation warnings for features that will be removed in the next version
   - Running `terraform plan` at each version lets you catch issues incrementally
   - State file format upgrades happen transparently, but once upgraded, you cannot downgrade

3. **You CANNOT downgrade**: Once you run `terraform plan` or `terraform apply` with a newer version, the state file is upgraded and older versions may refuse to read it.

### Recommended Upgrade Procedure

**Step 1: Preparation**
```
# Back up ALL state files before starting
# For each root module, either back up the GCS state bucket or use terraform state pull
```

**Step 2: Upgrade incrementally (recommended)**
```
1.11.2 -> 1.12.x (latest patch) -> 1.13.x (latest patch) -> 1.14.5
```

At each version:
1. Install the new Terraform binary
2. Update `required_version` in all `versions.tf` files
3. Run `terraform init -upgrade` in each root module
4. Run `terraform plan` and check for warnings/errors
5. Address any deprecation warnings before moving to the next version
6. Run `terraform apply` only after confirming the plan is clean

**Step 3: Update provider constraints if needed**
```
# After Terraform is upgraded, separately upgrade providers
terraform init -upgrade
terraform plan
```

**Step 4: For your specific repo, update all 33+ modules**

Given that you have many root modules, the upgrade should be done module-by-module or with a script:

```bash
# For each module directory:
for dir in org/projects iam/permissions networking/dns ...; do
  cd "$dir"
  # Update required_version in versions.tf
  terraform init -upgrade
  terraform plan
  cd -
done
```

### Critical Warnings

1. **State file backup is non-negotiable**: Your state lives in GCS (`liftit-tf-state`). Take a snapshot of the entire bucket before starting.

2. **CI/CD pipeline**: If you have CI/CD running Terraform, all runners must be updated to the new version simultaneously, or you risk state file version conflicts.

3. **Lock file regeneration**: After upgrading Terraform, run `terraform init -upgrade` to regenerate `.terraform.lock.hcl` files. These should be committed.

4. **Workspaces**: Your repo uses `terraform.workspace` in provider configs. Ensure you test the upgrade in all workspaces (not just the default).
